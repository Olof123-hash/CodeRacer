# Advanced Topics: Databases and Git

## Topic 1: Databases

We chose this topic because we knew from the beginning that we would have to implement some form of a database to pull our coding snippets from. It is extremely relevant to the project, because without a database the coding snippets would have to have been hard coded into the source files, so we would have to rebuild the program every time we added one.

Through this advanced topic we learnt a lot regarding GSON and using it for reading a JSON file and turning it into Java objects. We learnt that a database does not have to be a table with rows and columns: next to relational databases there are NoSQL databases, and a document store keeps data as JSON documents that have no fixed schema, so a field can be added later without changing a table. Since JSON is just text, a JSON file can work as a small document database for a project like ours. GSON converts JSON to Java objects by looking at the fields of a class, so the class acts as the schema. We also learnt that Java forgets the type of a generic list at runtime, so we needed a TypeToken to get a List<Snippet>, and that files packaged with the program are resources, loaded with getResourceAsStream instead of a file path.

We applied this with a Snippet class holding a body field, a DB.json file in resources with ten snippets, and a Database class that reads the JSON into a List<Snippet> and hands out a random one with getRandomSnippet(). The UI and race logic never touch the JSON, so all the database code is in one place.

From the implementation we learnt that we first added an SQLite dependency and then removed it: our data is read-only and small and is never searched or joined, so a real SQL database would only add a driver and tables without giving anything back. The cost we accepted is that we have no queries or transactions and cannot write anything back yet, so race scores are not saved. A challenge was the file loading, since a normal file path worked in the IDE but not once the program was packaged. We also found a bug: the method only checks if the list is null, but an empty JSON array is not null, so Random.nextInt(0) throws an exception. The impact was good, because adding a snippet is now just editing the JSON file and extra fields later need no redesign.

## Topic 2: Git

We chose this topic because the project is made by two people working on different computers, so without version control we would have been sending files back and forth and overwriting each other. It is relevant because we worked on separate parts at the same time, mostly one of us on the UI and the other on the game logic, and those parts had to end up in one program.

Through our research we learnt that a commit is a snapshot and a branch is just a pointer to a commit, which is why branching is cheap. We learnt about the staging area and that it decides what goes into a commit, and about the difference between a fast-forward merge and a real merge that needs a merge commit. A conflict happens when two people change the same lines. We also learnt why rewriting history with rebase is unsafe on a branch someone else has pushed, and we learnt about pull requests, .gitignore and git stash.

We applied this by giving every feature its own branch, for example feature/database, feature/race-engine, feature/race-panel and fix/engine-final, and merging them into main through pull requests so main kept working. We merged main back into open branches a few times instead of waiting until the end, used .gitignore after accidentally committing a desktop.ini file into resources, and used git stash to park unfinished work.

The biggest thing we learnt is that two people should not push to the same branch. We both worked on feature/game-window, so a push was rejected whenever the other had pushed first and we had to pull and merge, which is where the "Merge branch 'feature/game-window'..." commits come from. It works, but it turned that branch into a second main, which is what a branch should prevent. Merging main into a branch regularly did keep conflicts small. Two mistakes are still in our history: a branch called fix/<name> pushed without filling in the name, and commit messages that got worse when we were in a hurry, from "Load snippets from DB.json with Gson" to just "New". Since git log is the only place that says why something changed, that is a real loss. The impact was that we could work in parallel safely, and the history shows how the game was built up. One thing is still unfinished: main is behind feature/game-window, so the last UI work is pushed but not merged.
